## Per-Feature Details

### running-julia-test

- **Role:** Julia package developer with ordinary package-testing experience, using docs as the primary guide.
- **Use Case:** Run a complete package test suite, then target a specific test set for faster local iteration.
- **What they tried:** Created a disposable Julia package in `/tmp/running-julia-test.CLUd4i/DemoPkg`, added `test/runtests.jl`, ran `julia -e 'using Pkg; Pkg.test()'`, added the missing `Test` dependency, reran the full test command, then exercised `testrunner test/runtests.jl "basic tests"`, multiple named test sets, and line filtering with `L3:3`.
- **Discoverability:** The feature is easy to find from `README.md`, which lists `running-julia-test` as the standard and faster local Julia test workflow. The skill itself clearly separates full-suite `Pkg.test()`, targeted `testrunner`, and WarmTestRunner workflows.
- **Setup:** Full-suite testing worked after the package had a valid test dependency setup. A fresh `Pkg.generate` package with `using Test` in `test/runtests.jl` failed on Julia 1.12.6 until `Test` was added to the project/test environment. This is covered by the related `creating-julia-test-env` skill, but `running-julia-test` does not mention the prerequisite directly.
- **Functionality:** The documented full-suite command passed after setup:

  ```sh
  julia -e 'using Pkg; Pkg.test()'
  ```

  Result:

  ```text
  Test Summary: | Pass  Total  Time
  basic tests   |    1      1  0.0s
       Testing DemoPkg tests passed
  ```

  Targeted TestRunner commands also worked with an existing local `testrunner` installation:

  ```sh
  testrunner test/runtests.jl "basic tests"
  testrunner test/runtests.jl "basic tests" "struct tests"
  testrunner test/runtests.jl L3:3
  ```

  The observed totals matched the intended scope: 1 targeted test for one test set or one line range, and 2 tests for two named test sets.

- **Expected vs Actual Outcome:** The expected outcome was met. The only mismatch was that a brand-new generated package needed test-environment setup before the full-suite command could succeed.
- **Blocked steps:** Did not run the documented install commands for TestRunner.jl or WarmTestRunner.jl because they fetch external GitHub URLs. The local machine already had `~/.julia/bin/testrunner`, so TestRunner usage could still be tested. WarmTestRunner usage was not executed because adding it would require fetching an external package.
- **Friction points:** The first section says to run `Pkg.test()` but does not state that the package must already have a valid test environment, including `Test` for packages whose tests use `using Test`. Users who arrive here before reading `creating-julia-test-env` may see `Package Test not found in current path`.
- **Doc suggestions:** Add a short prerequisite note before the `Pkg.test()` command: "If this is a new package, first create the test environment as described in `creating-julia-test-env`; tests using `using Test` must have `Test` available in the package or test project." Also consider using `julia --project -e 'using Pkg; Pkg.test()'` in examples for consistency with other skills, even though Julia 1.12.6 activated the current package from the package directory during this test.

## Expected vs Actual Outcome

The feature met the expected outcome for a package with a configured test environment. `Pkg.test()` ran the full suite, and `testrunner` handled named test set and line-range workflows. The docs also correctly frame WarmTestRunner as a local iteration tool and `Pkg.test()` as the final-check path.

The main difference from a first-time user's expectation is that `running-julia-test` assumes test-environment setup has already happened. That is reasonable for a focused "run tests" skill, but a cross-link would prevent confusion.

## Issues Found

1. Medium: `running-julia-test` does not mention the prerequisite test-environment setup. A fresh Julia 1.12.6 package with `using Test` in `test/runtests.jl` failed with `Package Test not found in current path` until `Test` was added.
2. Low: The TestRunner and WarmTestRunner install commands require network access and external GitHub packages. That is expected, but the docs could tell users to treat installation as a one-time setup step and skip it if already installed.

## Suggestions

1. Add a prerequisite note and link to `creating-julia-test-env` at the start of `running-julia-test`.
2. Consider changing the full-suite command to `julia --project -e 'using Pkg; Pkg.test()'` for consistency and to make project selection explicit.
3. Add a one-line note under TestRunner installation: "If `command -v testrunner` already returns a path, you can skip installation."
